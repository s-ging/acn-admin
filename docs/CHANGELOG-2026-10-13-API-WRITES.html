3 Final architecture

Companies: base, draft, commit

Two local copies per company, never mixed (src/lib/companies/storage.ts):

localStorage keyHoldsWritten by
acn_company_{id}Base — last version fetched from the APIfetches and commit re-fetches only
acn_company_draft_{id}Draft — uncommitted editseditor autosave, sheet view
  • The editor autosaves the draft on every change; the draft is deleted the moment it matches the base.
  • The diff is always base → draft, computed by one engine.

Commit flow (src/lib/companies/sync.ts)

  1. Fetch the API version fresh.
  2. Conflict check — fields both the draft and the API changed since the base, differently. If any, nothing is sent; the dialog asks Overwrite with mine or Keep newswire version.
  3. Rebase the user's changes onto the fresh copy, so changes made elsewhere meanwhile are kept.
  4. Send the API-bound changes.
  5. Re-fetch — this becomes the new base.
  6. Verify — diff(new base, draft). Empty → draft deleted. Otherwise the draft keeps exactly the leftover (unlanded API changes plus local-only ones), so a retry resends only that.
  • New companies have a draft and no base. The first commit POSTs, re-keys the draft to the id the API returns, then continues at step 4.
  • Delete: API DELETE first; local copies are removed only if it succeeds. A company never committed is deleted locally only.

The diff engine (src/lib/companies/diff.ts)

  • FIELDS — every scalar field listed once, with label, section and where it goes on the wire (basicInfo.*, details.*, social links, or local + reason).
  • COLLECTIONS — every list keyed by a stable identity: sectors by name, listings by (mic, ticker), contacts / wire codes / RSS / relations / wire services by id. Sectors and listings are ordered (first = primary).
  • Each change carries display data for the dialog, a patch (applyChanges applies it to another copy — used for rebasing and for keeping only the leftover), and its wire ops or sync: 'local' with a reason.
  • findConflicts(mine, theirs) compares two change sets by key.
  • "" and null are equal; a cleared field is sent as "" (null on the update DTOs means "leave it").
  • Logos and the annual report are sent as filenames; data: upload previews are local-only.
  • A test asserts every CompanyFull field is covered by FIELDS, COLLECTIONS or IGNORED_FIELDS, so a new field cannot be silently skipped.

Requests (src/lib/api/write.ts)

No diffing — only ops → HTTP:

  • basicInfo / details ops are merged into one PUT /api/Companies/{id}.
  • Industry ops resolve the industry id by name via GET /api/Sectors (fetched lazily, once per session).
  • Listing and social-link ops are one request each.
  • createFromChanges POSTs a new company and throws if no id comes back, to avoid a duplicate create on retry.

Events

  • src/lib/events/write.ts: the benched write path is live. Payload uses the real DTO names — name, isPublished (boolean), organiserId, date-only YYYY-MM-DD dates, bare URL.
  • Save is local-first: the draft is written to acn_event_draft_{id} (or _new) before sending and cleared on success. A failed save is restored on the detail page with a notice; the next Save retries.
  • Detail page: Save, Delete (with confirm), Discard, a Published checkbox, and create at /events/new. The list's "+ New event" button is enabled.

Transport

  • src/lib/api/client.ts: new apiSend(method, path, body) beside apiGet — JSON body, Bearer header, ApiError, empty write body → null.
  • Token read from VITE_API_TOKEN until a login flow exists. Documented in .env.example; must not be set in a deployed build, since it ships to every browser.

4 Round 1 — write integration (as first built)

Approved scope: core writes plus sub-resources, automatic localStorage fallback, light tests.

  • client.ts: apiSend, VITE_API_TOKEN.
  • types.ts: write DTOs — CreateCompanyDto, UpdateCompanyDto, ApiCompanyBasicInfo, ApiCompanyDetailsWrite, SaveCompanyIndustryDto, CreateCompanyListingDto, UpdateCompanyListingDto, SaveCompanySocialLinkDto, SaveEventDto, ApiSector.
  • endpoints.ts: one function per write operation, fetchSectors, createdId.
  • write.ts (new): company → DTO mapping with its own diff against a fresh /full read, sub-resource planning, push.
  • companies/sync.ts (new): save to localStorage, then push; delete.
  • repository.ts: patchCachedCompany patches the cached list in place rather than forcing a 95-page re-sync. cache.ts: cacheSet takes an optional savedAt.
  • CommitModal / CompanyEditor: commit pushes to the API; Delete button added.
  • Events as in §3.
  • Mock server: accepts POST/PUT/DELETE on the write routes, logs them, returns { id } on create. Not persisted.
  • API-WIRING.md: "read-only" sections rewritten.

Problems found in review (led to round 2)

  • The store held either the API copy or the edited copy, so the true base was lost once a company was edited.
  • Editor edits lived only in memory until commit — a refresh lost them.
  • Two diffs disagreed: the dialog's computeDiff and the push's own diff covered different fields and keyed sectors/listings differently.
  • After a failed sync the editor's diff was empty, and the dialog offers no Commit button for an empty diff — a pending sync could not be retried.
  • Commit copied the local draft into the base instead of re-fetching what the API actually stored.

8 Behaviour changes users will notice

  • Company editor: Commit changes (was "Save changes"); the header shows the uncommitted count; edits survive a refresh; no "unsaved changes" prompt on leaving.
  • The commit dialog marks local-only changes and can stop on a conflict.
  • Opening a company from the list waits for the full API record (one request) instead of showing the list row first.
  • Companies created in the app get ids from 9,000,001.
  • Sheet edits become drafts, committed from the company editor.
  • Events are editable, deletable and creatable.

9 Open questions for the API team

  3. What do POST /api/Companies and POST /api/Events return? The code accepts a bare id or { id | companyId | compId | eventId }.
